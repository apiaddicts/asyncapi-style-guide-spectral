Every protocol binding must declare the fields its protocol requires, so that brokers and tools get the configuration they need to create and reach topics, queues and subscriptions.

The rule checks the bindings of servers, channels, operations and messages, both inline and in `components`, as well as the reusable bindings of `components.serverBindings`, `components.channelBindings`, `components.operationBindings` and `components.messageBindings`, each against the requirements of its kind and protocol. In AsyncAPI 2.x the operations are the `publish` and `subscribe` objects of each channel and the messages include each `oneOf` alternative; in AsyncAPI 3.x the operations are the entries of `operations` and the messages those of the channel `messages` maps and `components.messages`. The traits of an operation or message are merged into it first, as each version defines: in 2.x a trait overrides the object's own values, in 3.x the object's own values win. Trait definitions are not checked on their own, and a server, channel, operation, message or bindings object written as a `$ref` is checked once, where it is defined.

A required field that is missing, `null`, or an empty or blank string is a violation; `false`, `0`, empty lists and empty objects count as declared, and a protocol key written without a value counts as an empty binding. A nested requirement applies only when its parent object is present, and a requirement below a list applies to every item of the list. The finding is reported on the binding object, nested object or list item that lacks the field, or on the trait when the binding or the blank value comes only from a trait. By default the rule requires the fields that the AsyncAPI binding specifications mark as mandatory.

Parameters
----------

- `required_binding_props` — comma-separated list of the required binding fields. Each entry is written `kind.protocol.path`, optionally followed by a condition:
  - `kind` is `server`, `channel`, `operation` or `message`, or `*` for every kind; `protocol` is a binding key such as `kafka`, or `*` for every protocol (never an `x-` key). Both are case-insensitive.
  - `path` names the required field, case included. Nested fields are separated by dots (`queue.objectName`), and a name containing dots goes between brackets (`topicConfiguration[retention.ms]`). When a field along the path holds a list, the rest of the path is checked in each item of the list, so `consumers.endpoint` requires an `endpoint` in every consumer.
  - The last segment may list alternatives separated by `|`, such as `replicas|partitions`; declaring any one of them satisfies the entry.
  - A suffix `?field=value` applies the entry only when the top-level `field` of the same binding, read after merging traits, is exactly the string `value`; `?field!=value` applies it only when that field is absent, is not a string, or holds another string. Values are compared exactly, case included, so a field holding the number `12` never equals `12`. An entry takes at most one condition, its field is a single top-level name, and a `?` inside brackets belongs to the name.
  - Malformed entries (an unknown kind, fewer than three segments, an empty segment, `|` before the last segment, unbalanced brackets, a condition without field or value) are ignored. A list without usable entries falls back to the default, and a configured list replaces the default instead of extending it.

  Default: the mandatory fields of the AsyncAPI bindings that declare any.
  - `jms` server bindings: `jmsConnectionFactory`, and `name` and `value` in every item of `properties`.
  - `amqp` channel bindings: `exchange` when `is` is not `queue`, and `queue` when `is` is `queue`.
  - `googlepubsub` channel bindings: `schemaSettings` with its `encoding` and `name`; `googlepubsub` message bindings: `schema.name` when `schema` is present.
  - `ibmmq` channel bindings: `queue` when `destinationType` is `queue`, and `queue.objectName` whenever `queue` is present.
  - `pulsar` channel bindings: `namespace` and `persistence`.
  - `sns` channel bindings: `name`, `ordering.type` when `ordering` is present, and `policy.statements` when `policy` is present, each statement with `effect`, `principal` and `action`. `sns` operation bindings: `consumers`, each with `protocol`, `endpoint`, `rawMessageDelivery` and, when `redrivePolicy` is present, `redrivePolicy.deadLetterQueue`.
  - `sqs` channel bindings: `queue` and, when present, `deadLetterQueue`, each with `name`, `fifoQueue`, `redrivePolicy.deadLetterQueue` when `redrivePolicy` is present, and `policy.statements` when `policy` is present, each statement with `effect`, `principal` and `action`. `sqs` operation bindings: `queues`, each with `name`, `redrivePolicy.deadLetterQueue` when `redrivePolicy` is present, and `policy.statements` when `policy` is present, each statement with `effect`, `principal` and `action`.
  - `ros2` operation bindings: `role` and `node`.
