Message definitions are recommended to live in `components.messages`, where they can be reused, and to be referenced from the operations with `$ref`.

In AsyncAPI 2 the rule checks the `message` of every `publish` and `subscribe` operation in `channels`. A message whose `payload` schema is written inline is reported, and so is each alternative of a `oneOf` that is written inline instead of being a `$ref`. AsyncAPI 3 documents are not checked.

Noncompliant Code Example (AsyncAPI 2)
--------------------------------------

```yaml
asyncapi: 2.6.0
info:
  title: Orders Events
  version: 1.0.0
channels:
  orders.created:
    publish:
      message: # Noncompliant {{AAR026: Message schema is defined inline. It is recommended to define message schemas in 'components.messages' and reference them with $ref for reusability.}}
        name: OrderCreated
        contentType: application/json
        payload:
          type: object
          properties:
            orderId:
              type: string
  orders.updated:
    subscribe:
      message:
        oneOf:
          - name: OrderUpdated # Noncompliant {{AAR026: Message at index 0 in oneOf should use a $ref to a message defined in 'components.messages' for reusability.}}
            contentType: application/json
            payload:
              type: object
```

Compliant Solution (AsyncAPI 2)
-------------------------------

```yaml
asyncapi: 2.6.0
info:
  title: Orders Events
  version: 1.0.0
channels:
  orders.created:
    publish:
      message:
        $ref: '#/components/messages/OrderCreated'
components:
  messages:
    OrderCreated:
      name: OrderCreated
      contentType: application/json
      payload:
        $ref: './schemas/order-created.json'
```
