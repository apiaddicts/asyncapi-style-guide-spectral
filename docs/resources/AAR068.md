Every key of a bindings object must name a protocol binding allowed by the organization and defined by the document's AsyncAPI version, so that tools recognise each binding and apply its configuration.

The rule checks the bindings of servers, channels, operations, messages, operation traits and message traits, both inline and in `components`, as well as the reusable bindings of `components.serverBindings`, `components.channelBindings`, `components.operationBindings` and `components.messageBindings`. In AsyncAPI 2.x the operations are the `publish` and `subscribe` objects of each channel and the messages include each `oneOf` alternative; in AsyncAPI 3.x the operations are the entries of `operations` and the messages those of the channel `messages` maps and `components.messages`. A bindings object, message, operation or trait written as a `$ref` is checked once, where it is defined.

Each key is compared exactly as written, case included, with the list of allowed protocols, so a key outside the list is reported, and so are a misspelled or capitalised protocol such as `kafka-secure` or `Kafka` and a binding field placed directly in the bindings object. A key from the list that is an AsyncAPI protocol binding is also reported when the root `asyncapi` version predates it, for example `ros2` before 3.1.0 or `pulsar` before 2.6.0. Specification extensions (`x-` keys) are always accepted.

Parameters
----------

- `allowed-bindings` — comma-separated list of the allowed binding keys, such as `kafka,amqp`. Entries are trimmed and lower-cased, and entries that are not valid keys (letters, digits, `.`, `_` and `-`, starting with a letter or a digit) are ignored; when no entry is usable, the default list applies. Keys in the document are compared exactly with the list, so a capitalised key such as `Kafka` is never allowed, and `x-` keys are always accepted. A configured key outside the AsyncAPI specification, such as `rabbitmq`, is accepted in every version. An AsyncAPI protocol binding is only accepted from the version that introduced it, read from the major and minor parts of the root `asyncapi` value; no key is version-checked when that value cannot be read. Default: `http,ws,kafka,anypointmq,amqp,amqp1,mqtt,mqtt5,nats,jms,sns,solace,sqs,stomp,redis,mercure,ibmmq,googlepubsub,pulsar,ros2`.

  | Binding keys | Available from AsyncAPI |
  |--------------|-------------------------|
  | `http`, `ws`, `kafka`, `amqp`, `amqp1`, `mqtt`, `mqtt5`, `nats`, `jms`, `sns`, `sqs`, `stomp`, `redis` | 2.0.0 |
  | `mercure`, `ibmmq` | 2.1.0 |
  | `anypointmq` | 2.2.0 |
  | `solace` | 2.3.0 |
  | `googlepubsub` | 2.5.0 |
  | `pulsar` | 2.6.0 |
  | `ros2` | 3.1.0 |

Noncompliant Code Example (AsyncAPI 2)
--------------------------------------

```yaml
asyncapi: 2.5.0
info:
  title: Orders Events
  version: 1.0.0
servers:
  production:
    url: broker.quality.es:9093
    protocol: kafka-secure
  analytics:
    url: pulsar.quality.es:6651
    protocol: pulsar
    bindings:
      pulsar: # Noncompliant {{AAR068: Server binding 'pulsar' requires AsyncAPI 2.6.0 or later.}}
        tenant: quality
channels:
  orders.created:
    bindings:
      kafka-secure: # Noncompliant {{AAR068: Channel binding 'kafka-secure' is not an allowed protocol.}}
        partitions: 12
    subscribe:
      operationId: receiveOrderCreated
      message:
        bindings:
          Kafka: # Noncompliant {{AAR068: Message binding 'Kafka' is not an allowed protocol.}}
            key:
              type: string
        payload:
          type: object
```
