The two operations of a processor (a function that consumes from one topic and produces to another) must share the same `x-scs-function-name`, so that the JAPI generator links them as a single processor.

The rule groups by their `x-scs-function-name` value the `publish` and `subscribe` operations of the root channels in AsyncAPI 2.x, and the root `operations` with `action: send` or `action: receive` in AsyncAPI 3.x. Operations without the extension, or with an empty value, are ignored.

Each value must be paired one-to-one: it needs as many producing operations (`publish` / `send`) as consuming ones (`subscribe` / `receive`). Every operation left without a counterpart is reported at its `x-scs-function-name` (when one side has more operations, the last ones in document order). This covers a value used by a single operation, a misspelled value that breaks a pair, and a value repeated on the same side.

Noncompliant Code Example (AsyncAPI 2)
--------------------------------------

```yaml
asyncapi: 2.6.0
info:
  title: Orders Processor
  version: 1.0.0
channels:
  orders.evt.order.created:
    publish:
      operationId: consumeOrderCreated
      x-scs-function-name: enrichOrder # Noncompliant {{AAR061: The x-scs-function-name 'enrichOrder' must be paired one-to-one between a publish/send and a subscribe/receive operation.}}
  orders.evt.order.enriched:
    subscribe:
      operationId: produceOrderEnriched
      x-scs-function-name: enrichOrders # Noncompliant {{AAR061: The x-scs-function-name 'enrichOrders' must be paired one-to-one between a publish/send and a subscribe/receive operation.}}
```

Compliant Solution (AsyncAPI 2)
-------------------------------

```yaml
asyncapi: 2.6.0
info:
  title: Orders Processor
  version: 1.0.0
channels:
  orders.evt.order.created:
    publish:
      operationId: consumeOrderCreated
      x-scs-function-name: enrichOrder
  orders.evt.order.enriched:
    subscribe:
      operationId: produceOrderEnriched
      x-scs-function-name: enrichOrder
```

Noncompliant Code Example (AsyncAPI 3)
--------------------------------------

```yaml
asyncapi: 3.0.0
info:
  title: Payments Processor
  version: 1.0.0
channels:
  paymentRequested:
    address: payments.cmd.payment.requested
  paymentAuthorized:
    address: payments.evt.payment.authorized
  paymentRejected:
    address: payments.evt.payment.rejected
operations:
  consumePaymentRequested:
    action: receive
    channel:
      $ref: '#/channels/paymentRequested'
    x-scs-function-name: authorizePayment
  producePaymentAuthorized:
    action: send
    channel:
      $ref: '#/channels/paymentAuthorized'
    x-scs-function-name: authorizePayment
  producePaymentRejected:
    action: send
    channel:
      $ref: '#/channels/paymentRejected'
    x-scs-function-name: authorizePayment # Noncompliant {{AAR061: The x-scs-function-name 'authorizePayment' must be paired one-to-one between a publish/send and a subscribe/receive operation.}}
```

Compliant Solution (AsyncAPI 3)
-------------------------------

```yaml
asyncapi: 3.0.0
info:
  title: Payments Processor
  version: 1.0.0
channels:
  paymentRequested:
    address: payments.cmd.payment.requested
  paymentAuthorized:
    address: payments.evt.payment.authorized
  paymentRejected:
    address: payments.evt.payment.rejected
operations:
  consumePaymentRequested:
    action: receive
    channel:
      $ref: '#/channels/paymentRequested'
    x-scs-function-name: authorizePayment
  producePaymentAuthorized:
    action: send
    channel:
      $ref: '#/channels/paymentAuthorized'
    x-scs-function-name: authorizePayment
  producePaymentRejected:
    action: send
    channel:
      $ref: '#/channels/paymentRejected'
```
